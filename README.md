# CommuteOS

A personal mobility decision engine — not a transit app. It learns a commuter's routing preferences (speed vs. reliability, walking tolerance, transfer aversion) and proactively recommends real-time travel decisions. Starting domain: NYC-metro transit (MTA, NJ Transit, PATH).

Full product rationale lives in [`CommuteOS PRD.txt`](./CommuteOS%20PRD.txt). Open decisions and pending items are tracked in [`OPEN_QUESTIONS.md`](./OPEN_QUESTIONS.md).

**Scope decisions:** NYC-metro only (no plans to expand to other cities); a real multi-user product with accounts starting in Phase 2, not a single-user personal tool.

## Current phase

**Phase 1 — Real-Time Multi-Agency Transit Intelligence** (done: MTA, PATH, and NJ Transit rail + bus all live). **Phase 2 — Personal Commute Memory** (done: learned preferences, nightly-job stand-in). **Phase 3 — AI Commute Agent** (done: deterministic decision engine, LLM phrasing, recommendation tracking).

All three phases have working code end-to-end as of this rapid-build round — this does NOT mean Phase 1's real exit criteria are met (two weeks of daily personal use hasn't happened) or Phase 3's cold-start requirement is satisfied (no real 2-week trip history exists yet, only a synthetic demo seed - see `backend/app/jobs/seed_demo_trips.py`). "Built" and "validated against real usage" are different claims; see `OPEN_QUESTIONS.md` for what's still genuinely open.

## Status

- Flutter project scaffolded (`flutter create`), package id `com.commuteos.commuteos`
- Dev toolchain verified working: Flutter 3.44.8 (stable), JDK 17, Android SDK (build-tools 36.0.0), `flutter doctor` clean for Android target
- **Cross-agency architecture** (`lib/transit/`) — a `TransitStation`/`TransitService`/`TransitArrival` abstraction so search, favorites, and the arrivals screen work identically regardless of agency. Each agency (`lib/mta/`, `lib/path/`) adapts its own data shape (GTFS-RT protobuf, PATH's JSON) to these interfaces; a feed failure in one agency can't affect another.
- **MTA live subway arrivals working end-to-end** (`lib/mta/`) — fetches the unauthenticated MTA GTFS-realtime feed, parses the protobuf `TripUpdate`s, and renders live arrivals.
- **PATH live arrivals** (`lib/path/`) — all 13 PATH stations, fetched from the same (unofficial, unauthenticated) JSON endpoint that powers PATH's own website. No official public PATH API exists — see `OPEN_QUESTIONS.md` for the sourcing rationale. Includes staleness detection: if the feed's own timestamps go stale, the UI shows a "live data unavailable" banner rather than presenting old data as current.
- **All ~509 stations (MTA + PATH) searchable in one unified list, correctly grouped and sorted** — bundles MTA's published station list (`assets/data/mta_stations.csv`) plus PATH's 13 hardcoded stations; tapping a station shows live arrivals split into direction tabs. Verified on an Android emulator against the real feed for multiple stations. Stations sort in natural numeric order (1, 2, 3…96, 103, 110, not string order), and station names that map to more than one physical station (e.g. multiple "Canal St"s, some connected, some not) show as a single grouped row with a picker on tap rather than duplicate rows.
- **Favorites** (`lib/favorites/`) — the app opens to a favorites list (local device storage only, no account/backend), with an empty state prompting a first search. Favorite/unfavorite a whole station via a star icon, shared between the favorites view and the full search screen so both stay in sync. Favorites are keyed per-agency-per-station so an MTA and a PATH station can never collide.
- **Backend** (`backend/`) — FastAPI + SQLAlchemy 2.0 + Alembic, matching the PRD's `users`/`trips`/`preferences` schema, running against a real local PostgreSQL instance (installed and verified — see `OPEN_QUESTIONS.md` for the setup story). Auth: bcrypt + JWT, `/auth/signup`, `/auth/login`, `/users/me`. Every signup gets a `preferences` row at PRD defaults immediately.
- **Mobile app talks to the backend** (`lib/account/`) — an optional account screen (signup/login/logout), reachable from the favorites screen's app bar; browsing and favoriting still never require an account. Logging in turns on passive trip logging: opening any station's arrivals screen posts a trip data point to the backend for logged-in users only. `dest_stop` is left null since the app doesn't yet capture a real destination. Reaches the backend over USB (`adb reverse`) during development, not Wi-Fi — see `OPEN_QUESTIONS.md` for why.
- **Phase 2 — learned preferences** (`backend/app/preference_engine.py`, `GET/POST /preferences/me`) — a nightly-batch-job stand-in (run manually via `python -m app.jobs.recompute_preferences` for now; real OS-level scheduling is a deployment concern, not solved here) that recomputes `walking_tolerance_m` from trip history. `transfer_aversion_score` is deliberately left at its neutral default — the PRD's real signal for it (direct-vs-transfer route comparisons) doesn't exist in the data model yet, and computing a fake number would be worse than an honest "not yet knowable." A seed script (`backend/app/jobs/seed_demo_trips.py`) generates realistic synthetic trip history for demoing, since no real 2-week usage history exists yet. Flutter: a "What CommuteOS has learned" screen shows the plain-data numbers, per Phase 2's exit criteria.
- **Phase 3 — AI Commute Agent** (`backend/app/decision_engine.py`, `backend/app/llm_phrasing.py`, `POST /recommendations`) — MTA and PATH real-time fetching ported to Python (`backend/app/transit/`, verified against live feeds) so the backend can score candidate routes itself, matching the PRD's architecture. The decision engine is deterministic (no LLM), scoring candidates by predicted arrival time weighted by the user's `reliability_pref` against each route's confidence (live vs. stale data — a documented, scoped-down stand-in for the PRD's "recent delay variance," which isn't computable yet from current trip data). The LLM phrasing layer (Groq, OpenAI-compatible API) turns the engine's structured output into one sentence, never sees raw trip history, and falls back to a deterministic template if no API key is configured (none is yet — user has a Groq key to add later). `PATCH /trips/{id}/outcome` and `GET /trips/accuracy` implement the PRD's trust-preserving design (track whether recommendations were followed and how accurate they were). Flutter: a "What should I take?" screen defaults to auto-discovery from the user's confirmed home/office stations (`GET /recommendations/from-home-office`, no setup needed), falling back to manually picking 2+ favorited stations to compare when auto-discovery isn't eligible yet (home/office unconfirmed, or not yet resolvable to a real candidate route).
- **Home/office inference** (`backend/app/home_office_engine.py`, `GET/POST /home-office/me`, `POST /home-office/me/infer`, `POST /home-office/me/confirm`) — infers a user's home and office as **station codes**, not the lat/lng the PRD's schema describes: `Trip` only records an `origin_stop` code, and syncing a station→coordinate lookup to the backend was a scope cut for now (PATH doesn't even have consistent coordinates). Heuristic: the most common `origin_stop` among a user's before-noon trips is "home," the most common among at-or-after-noon trips is "office"; each needs at least 3 trips in that slot before inferring anything, so a new account shows nothing rather than a guess from one data point. Wired into the same batch job as preference recomputation (`python -m app.jobs.recompute_preferences`). The PRD's "confirmed once via a simple prompt" step is a real `home_office_confirmed` flag — an unconfirmed inference is never treated as authoritative for scheduling. Flutter: a card on the preferences screen shows the inferred stations with a "Yes, that's right" confirm action.
- **Proactive, content-aware commute notifications — real push, on a real daily schedule** (`backend/app/jobs/send_commute_notifications.py`, `backend/app/notify_service.py`, `lib/account/push_registration_service.dart`) — superseded the earlier local-only, fixed-time reminder (which just said "check your commute" on a timer, regardless of conditions). A scheduled job runs the real decision engine + LLM phrasing against a user's confirmed home/office station and pushes the *actual* recommendation ("Your usual PATH is delayed, take NJ Transit instead"), the same pipeline `/recommendations` uses (factored into `app/recommendation_builder.py` so both share one implementation). Push delivery is real Firebase Cloud Messaging (`notify_service.py` uses the Firebase Admin SDK server-side; `push_registration_service.dart` requests the Android 13+ notification permission and registers this device's real FCM token via `PUT /users/me/fcm-token`) — falls back to logging instead of sending if no Firebase project is configured, so the backend still starts up fine without one. A real gap surfaced building this: MTA/PATH need a specific route/direction to fetch arrivals, but trip logging never captured one (only station + agency) — fixed by having `ArrivalsScreen` log the route/direction of whichever arrival was soonest when the screen loaded (a real observed signal, not guessed), stored as `Trip.route_or_direction` and carried into `User.home_route_or_direction`/`office_route_or_direction` by the home/office inference engine. NJT rail/bus don't need this (a station code alone is enough there).
- **The commute-notification job now runs automatically, once daily** (`backend/app/routers/internal.py`, `.github/workflows/commute-notifications.yml`) — Render's free tier has no built-in cron product, and the web service itself spins down when idle, so an in-process scheduler alone couldn't reliably fire on a schedule. Instead: `POST /internal/run-commute-job` (guarded by a shared secret via the `X-Internal-Secret` header, constant-time-compared, disabled with a 503 if unconfigured) triggers the job; a GitHub Actions scheduled workflow calls it once daily at 7:45 AM US Eastern. GitHub Actions cron is UTC-only with no DST awareness, so the workflow declares *two* cron schedules (one for EDT, one for EST) and checks the real current UTC offset at run time to make sure only the correct one for the current time of year actually calls the backend — exactly correct year-round, no manual updates needed each DST switch. Also supports a manual `workflow_dispatch` trigger for testing without waiting for the schedule. 5 new backend tests for the internal endpoint's auth (missing secret, wrong secret, unconfigured, success, and a regression guard that it uses its own DB session rather than a per-request one).
- **Design system + full visual pass** (`lib/design/`) — a dark-first, transit-app-modern theme (`theme.dart`: near-black background, mint/teal accent reserved for live data and primary actions, a real type scale, consistent spacing/radius constants) applied across every screen, replacing the original default-Material look. Shared components (`components.dart`: `AppCard`, `AppBadge`/agency-colored badges, `LiveStatusPill`, `SectionHeader`, `EmptyState`, `MinutesAway`, `AppLoader`) keep every screen visually consistent instead of each one inventing its own row/empty-state style. Navigation was restructured from appbar icons into a persistent bottom nav (`root_shell.dart`: Favorites / Search / Account, each with its own nested `Navigator` so pushing a detail screen like arrivals doesn't hide the tab bar or lose other tabs' state). Caught and fixed a real, previously-undetected build bug along the way: adding `flutter_local_notifications` (done in the home/office round) needed Android core library desugaring enabled, which was never actually build-verified before — `flutter analyze`/`flutter test` don't invoke Gradle, so this had been silently broken since that round; `flutter build apk --debug` now succeeds. This pass is visual/navigational only — no screen's underlying data flow or repository logic changed.
- **Real line colors, not generic badges** — route/line indicators now use each system's actual published colors instead of a single flat agency color. MTA: a hardcoded lookup table of NYCT's own published subway line colors keyed by route ID (`lib/design/components.dart`, `_mtaRouteColors`) — MTA's GTFS-RT feed carries no color data itself, and the official set is small/fixed enough that a static table is the right call rather than an external source. PATH: parses the real `lineColor` hex field the feed already publishes per arrival (`lib/path/path_arrival.dart`, `parsePathRouteColors`) — previously fetched but silently discarded. Occasionally a PATH arrival's `lineColor` is more than one comma-separated hex value (a train that runs via more than one PATH line); the first is used for the badge, malformed values are dropped rather than guessed at. Text-on-badge contrast (black vs. white) is chosen automatically per color's luminance so light colors (MTA's yellow N/Q/R/W, gray L) stay legible. Station-level route lists (search/favorites/recommendation rows) now render as small colored `RouteChip`s per line instead of joined plain text.
- **12-hour clock time shown alongside the minutes-away countdown** (`lib/design/components.dart`, `formatClockTime`) — each arrival row now shows a real "5:24 PM" line under the destination/headsign, in addition to the existing "N min" countdown. Per user feedback that minutes-only wasn't enough (real station displays and Google Maps both show the actual clock time too), added rather than replacing anything already shown.
- **Destination grouping + filter chips for multi-destination directions** (`lib/transit/arrivals_screen.dart`, `groupArrivalsByDestination`) — a direction that serves more than one real destination (e.g. WTC's "To New Jersey," which mixes Newark-bound and Hoboken-bound PATH trains) now shows arrivals clustered under a destination header ("NEWARK", "HOBOKEN") instead of one interleaved list sorted purely by time, plus tappable "All / Newark / Hoboken" filter chips to collapse down to a single destination. Falls back to exactly the prior flat list when a direction has only one destination, or none at all (MTA's GTFS-RT feed never provides a headsign, so MTA stations are entirely unaffected). Built after investigating a user-reported discrepancy that turned out to be a real UX gap, not a data bug — see `OPEN_QUESTIONS.md`.
- **NJ Transit rail — real-time, live end-to-end** (`backend/app/transit/njt_rail.py`, `lib/njt/`) — developer account approved 2026-08-01; verified against the real API before writing any parser, the same way MTA/PATH were. Not the legacy SOAP/XML endpoint the original scaffold worried about — `raildata.njtransit.com/api/TrainData/...` is a modern JSON API (NJT's own docs list the host as `raildata.njt.gov`, which does not resolve; `.njtransit.com` is the real one). Auth is real username/password → 24h token, cached and reused rather than re-minted per call. NJT's feed gives a *scheduled* departure time plus a separate delay-in-seconds field (`SEC_LATE`, which can be negative for an early train) — the two must be added together to get a real predicted time, unlike MTA/PATH which report one absolute prediction directly. 172 rail stations (`assets/data/njt_rail_stations.csv`, built from NJT's own static GTFS feed via `backend/scripts/build_njt_rail_stations.py`) bundled into the unified search/favorites list. Because NJT rail requires a real credential (unlike MTA/PATH, which are public/unauthenticated), the credentials live server-side only — the Flutter app calls our own hosted backend (`GET /transit/njt-rail/{station_code}`) rather than NJT's API directly, so nothing extractable from the APK.
- **NJ Transit bus — real-time, live end-to-end** (`backend/app/transit/njt_bus.py`, `lib/njt/njt_bus_*.dart`) — initially assumed schedule-only (the first documented endpoint, `BUSDV2/getBusRoutes`, is static-only), but NJT's actual bus real-time API turned out to be a *different* one (`GTFSG2`), standard GTFS-realtime protobuf — the same format MTA already uses, and the same `gtfs_realtime_bindings` dependency. Real quirk: NJT's bus feed reports an empty `route_id` on every update, so the backend joins each update's `trip_id` against a bundled static lookup (`app/data/njt_bus_trip_routes.csv`, ~46k rows, built from NJT's static bus GTFS) to know which line an arrival belongs to. Scoped to a NYC-metro "core" bounding box (~5,100 stops, Hudson/Essex/Union/Bergen counties, roughly) rather than NJT's full statewide ~17k-stop network, per the PRD's NYC-metro-only scope decision — also excludes ~129 Newark Light Rail stops that share the same source file but are a different transit mode. No official per-line colors exist in NJT's bus GTFS (unlike rail), so bus routes render in a single agency color rather than per-line. Same backend-proxy pattern as rail for credentials.
- **Backend hosting verified with a 3rd real external credential** — NJT rail/bus both needed real third-party credentials (username/password) proxied through the now-hosted backend (see the hosting entry above), confirming the "credentials live server-side, app never holds them" pattern generalizes cleanly beyond the LLM key.

## Getting started

### Mobile app (Flutter)

```
flutter pub get
flutter run
```

Requires the Flutter SDK and Android SDK on PATH — see `flutter doctor` to verify your environment.

### Backend (FastAPI)

```
cd backend
python -m venv .venv
.venv\Scripts\pip install -e ".[dev]"
copy .env.example .env    # then edit DATABASE_URL/SECRET_KEY as needed
.venv\Scripts\python -m pytest        # run tests (SQLite, no Postgres needed)
.venv\Scripts\python -m alembic upgrade head   # requires a running local Postgres (see below)
.venv\Scripts\python -m uvicorn app.main:app --port 8001 --reload
```

Runs on **port 8001**, not FastAPI's usual 8000 default — this dev environment already has an unrelated project on 8000. Requires a local PostgreSQL instance with a `commuteos`/`commuteos` user and database (`CREATE USER commuteos WITH PASSWORD 'commuteos'; CREATE DATABASE commuteos OWNER commuteos;`), matching `DATABASE_URL` in `.env.example`. This is only needed for *local* backend development — the app itself now talks to a real hosted backend by default (see below), not localhost.

### Hosted backend

The backend is deployed on **Render's free tier** (`backend/render.yaml`: build/start commands, health check at `/health`, migrations run automatically via `alembic upgrade head` on every deploy), backed by a free **Neon** Postgres instance. The app's `apiBaseUrl` (`lib/account/api_config.dart`) points at the hosted URL — no more USB/`adb reverse` tunnel or "backend only runs on my laptop" requirement. Free-tier tradeoff: the Render service spins down after ~15 minutes of no traffic, so the first request after a while takes a few extra seconds to wake it back up — expected, not a bug. Env vars (`DATABASE_URL`, `SECRET_KEY`, `GROQ_API_KEY`, etc.) are set directly in Render's dashboard, never committed.

## Tech stack (per PRD)

- Mobile: Flutter
- Backend (Phase 2+): FastAPI + PostgreSQL
- AI (Phase 3+): LLM used only for phrasing structured decision-engine output into natural language, never for the decision itself
- Maps: MapLibre + OSM
- Data: GTFS-RT, isolated per-agency parsers so one feed breaking doesn't break the others
