# CommuteOS

A personal mobility decision engine — not a transit app. It learns a commuter's routing preferences (speed vs. reliability, walking tolerance, transfer aversion) and proactively recommends real-time travel decisions. Starting domain: NYC-metro transit (MTA, NJ Transit, PATH).

Full product rationale lives in [`CommuteOS PRD.txt`](./CommuteOS%20PRD.txt). Open decisions and pending items are tracked in [`OPEN_QUESTIONS.md`](./OPEN_QUESTIONS.md).

**Scope decisions:** NYC-metro only (no plans to expand to other cities); a real multi-user product with accounts starting in Phase 2, not a single-user personal tool.

## Current phase

**Phase 1 — Real-Time Multi-Agency Transit Intelligence** (done: MTA, PATH, NJ Transit rail + bus, and LIRR all live). **Phase 2 — Personal Commute Memory** (done: learned preferences, nightly-job stand-in). **Phase 3 — Four Named AI Features, all four now built** (re-scoped 2026-08-07 into **Behavior AI**, **Commute AI**, **Schedule AI**, **Chat AI** — see the PRD's Phase 3 for the full plan. **Behavior AI** — `backend/app/behavior_engine.py` + `GET /behavior/me`, four passive signals: feed accuracy, direction choice, timing buffer (a real passive data source — native Android Activity Recognition, see `lib/behavior/departure_detector.dart`), and typical arrival time. **Chat AI** — `backend/app/chat_ai.py` + `POST /chat` (one endpoint, both tiers — auth is optional, unlocking the personalized tier when present) + `lib/chat/`; stateless tier answers free-text transit questions from live data alone, personalized tier answers "what do I usually take from here"-style questions via the exact same engine Commute AI uses. **Schedule AI** — `backend/app/schedule_engine.py`, fires an hour ahead of each user's own learned departure hour and phrases one of three real severities (on time / delayed with a genuine minutes-late number / no live data, falling back to a real substitute route). **Commute AI** — `backend/app/commute_engine.py` + `GET /commute/{agency}/{code}` + `lib/commute/`; ranks a station's own real routes/directions and, when there's enough history, flags "take X instead of your usual Y." **Phase 3's exit criterion is met with a real automated test**, not just a design claim: `test_personalized_answer_matches_commute_ai_exactly` proves Chat AI's personalized tier and Commute AI produce byte-identical phrased answers for the same station/user, since both call the one shared `commute_engine.rank_best` ranking path.

All work below reflects what's actually shipped as of this rapid-build round — this does NOT mean Phase 1's real exit criteria are met (two weeks of daily personal use hasn't happened) or Phase 3's cold-start requirement is satisfied (no real 2-week trip history exists yet, only a synthetic demo seed - see `backend/app/jobs/seed_demo_trips.py`). "Built" and "validated against real usage" are different claims; see `OPEN_QUESTIONS.md` for what's still genuinely open.

No official public PATH API exists — see `OPEN_QUESTIONS.md` for the sourcing rationale. Includes staleness detection: if the feed's own timestamps go stale, the UI shows a "live data unavailable" banner rather than presenting old data as current.

Verified on an Android emulator against the real feed for multiple stations. Stations sort in natural numeric order (1, 2, 3…96, 103, 110, not string order), and station names that map to more than one physical station (e.g. multiple "Canal St"s, some connected, some not) show as a single grouped row with a picker on tap rather than duplicate rows.

Favorite/unfavorite a whole station via a star icon, shared between the favorites view and the full search screen so both stay in sync. Favorites are keyed per-agency-per-station so an MTA and a PATH station can never collide.
- **Backend** (`backend/`) — FastAPI + SQLAlchemy 2.0 + Alembic, matching the PRD's `users`/`trips`/`preferences` schema, running against a real local PostgreSQL instance (installed and verified — see `OPEN_QUESTIONS.md` for the setup story). Auth: bcrypt + JWT, `/auth/signup`, `/auth/login`, `/users/me`. Every signup gets a `preferences` row at PRD defaults immediately.
- **Mobile app talks to the backend** (`lib/account/`) — an optional account screen (signup/login/logout), reachable from the favorites screen's app bar; browsing and favoriting still never require an account. Logging in turns on passive trip logging: opening any station's arrivals screen posts a trip data point to the backend for logged-in users only. `dest_stop` is left null since the app doesn't yet capture a real destination. Reaches the backend over USB (`adb reverse`) during development, not Wi-Fi — see `OPEN_QUESTIONS.md` for why.
- **Phase 2 — learned preferences** (`backend/app/preference_engine.py`, `GET/POST /preferences/me`) — a nightly batch job (`python -m app.jobs.recompute_preferences`, run automatically once nightly via `POST /internal/run-preference-recompute-job` + a GitHub Actions scheduled workflow, same mechanism as the commute-notification job) that recomputes `walking_tolerance_m` from trip history. `transfer_aversion_score` is deliberately left at its neutral default — the PRD's real signal for it (direct-vs-transfer route comparisons) doesn't exist in the data model yet, and computing a fake number would be worse than an honest "not yet knowable." A seed script (`backend/app/jobs/seed_demo_trips.py`) generates realistic synthetic trip history for demoing, since no real 2-week usage history exists yet. Flutter: a "What CommuteOS has learned" screen shows the plain-data numbers, per Phase 2's exit criteria — showing "Still learning" instead of a number for any value that isn't actually backed by enough real trip history yet (`trip_count`/`walking_tolerance_learned`, exposed by the API), rather than presenting an untouched default as a real, confident measurement.
- **Phase 3 — AI Commute Agent** (`backend/app/decision_engine.py`, `backend/app/llm_phrasing.py`, `POST /recommendations`) — MTA and PATH real-time fetching ported to Python (`backend/app/transit/`, verified against live feeds) so the backend can score candidate routes itself, matching the PRD's architecture. The decision engine is deterministic (no LLM), scoring candidates by predicted arrival time weighted by the user's `reliability_pref` against each route's confidence (live vs. stale data — a documented, scoped-down stand-in for the PRD's "recent delay variance," which isn't computable yet from current trip data). The LLM phrasing layer (Groq, OpenAI-compatible API) turns the engine's structured output into one sentence, never sees raw trip history, and falls back to a deterministic template if no API key is configured (none is yet — user has a Groq key to add later). `PATCH /trips/{id}/outcome` and `GET /trips/accuracy` implement the PRD's trust-preserving design (track whether recommendations were followed and how accurate they were). Flutter: a "What should I take?" screen defaults to auto-discovery from the user's confirmed home/office stations (`GET /recommendations/from-home-office`, no setup needed), falling back to manually picking 2+ favorited stations to compare when auto-discovery isn't eligible yet (home/office unconfirmed, or not yet resolvable to a real candidate route).
- **Home/office inference** (`backend/app/home_office_engine.py`, `GET/POST /home-office/me`, `POST /home-office/me/infer`, `POST /home-office/me/confirm`) — infers a user's home and office as **station codes**, not the lat/lng the PRD's schema describes: `Trip` only records an `origin_stop` code, and syncing a station→coordinate lookup to the backend was a scope cut for now (PATH doesn't even have consistent coordinates). Heuristic: the most common `origin_stop` among a user's before-noon trips is "home," the most common among at-or-after-noon trips is "office"; each needs at least 3 trips in that slot before inferring anything, so a new account shows nothing rather than a guess from one data point. Wired into the same batch job as preference recomputation (`python -m app.jobs.recompute_preferences`, now running automatically once nightly). The PRD's "confirmed once via a simple prompt" step is a real `home_office_confirmed` flag — an unconfirmed inference is never treated as authoritative for scheduling. Flutter: a card on the preferences screen shows the inferred stations with a "Yes, that's right" confirm action.
- **Proactive, content-aware commute notifications — real push, on a real daily schedule** (`backend/app/jobs/send_commute_notifications.py`, `backend/app/notify_service.py`, `lib/account/push_registration_service.dart`) — superseded the earlier local-only, fixed-time reminder (which just said "check your commute" on a timer, regardless of conditions). A scheduled job runs the real decision engine + LLM phrasing against a user's confirmed home/office station and pushes the *actual* recommendation ("Your usual PATH is delayed, take NJ Transit instead"), the same pipeline `/recommendations` uses (factored into `app/recommendation_builder.py` so both share one implementation). Push delivery is real Firebase Cloud Messaging (`notify_service.py` uses the Firebase Admin SDK server-side; `push_registration_service.dart` requests the Android 13+ notification permission and registers this device's real FCM token via `PUT /users/me/fcm-token`) — falls back to logging instead of sending if no Firebase project is configured, so the backend still starts up fine without one. A real gap surfaced building this: MTA/PATH need a specific route/direction to fetch arrivals, but trip logging never captured one (only station + agency) — fixed by having `ArrivalsScreen` log the route/direction of whichever arrival was soonest when the screen loaded (a real observed signal, not guessed), stored as `Trip.route_or_direction` and carried into `User.home_route_or_direction`/`office_route_or_direction` by the home/office inference engine. NJT rail/bus don't need this (a station code alone is enough there).
- **The commute-notification job now runs automatically, once daily** (`backend/app/routers/internal.py`, `.github/workflows/commute-notifications.yml`) — Render's free tier has no built-in cron product, and the web service itself spins down when idle, so an in-process scheduler alone couldn't reliably fire on a schedule. Instead: `POST /internal/run-commute-job` (guarded by a shared secret via the `X-Internal-Secret` header, constant-time-compared, disabled with a 503 if unconfigured) triggers the job; a GitHub Actions scheduled workflow calls it once daily at 7:45 AM US Eastern. GitHub Actions cron is UTC-only with no DST awareness, so the workflow declares *two* cron schedules (one for EDT, one for EST) and checks the real current UTC offset at run time to make sure only the correct one for the current time of year actually calls the backend — exactly correct year-round, no manual updates needed each DST switch. Also supports a manual `workflow_dispatch` trigger for testing without waiting for the schedule. 5 new backend tests for the internal endpoint's auth (missing secret, wrong secret, unconfigured, success, and a regression guard that it uses its own DB session rather than a per-request one).

Per user feedback that minutes-only wasn't enough (real station displays and Google Maps both show the actual clock time too), added rather than replacing anything already shown.
- **Destination grouping + filter chips for multi-destination directions** (`lib/transit/arrivals_screen.dart`, `groupArrivalsByDestination`) — a direction that serves more than one real destination (e.g. WTC's "To New Jersey," which mixes Newark-bound and Hoboken-bound PATH trains) now shows arrivals clustered under a destination header ("NEWARK", "HOBOKEN") instead of one interleaved list sorted purely by time, plus tappable "All / Newark / Hoboken" filter chips to collapse down to a single destination. Falls back to exactly the prior flat list when a direction has only one destination, or none at all (MTA's GTFS-RT feed never provides a headsign, so MTA stations are entirely unaffected). Built after investigating a user-reported discrepancy that turned out to be a real UX gap, not a data bug — see `OPEN_QUESTIONS.md`.
- **NJ Transit rail — real-time, live end-to-end** (`backend/app/transit/njt_rail.py`, `lib/njt/`) — developer account approved 2026-08-01; verified against the real API before writing any parser, the same way MTA/PATH were. Not the legacy SOAP/XML endpoint the original scaffold worried about — `raildata.njtransit.com/api/TrainData/...` is a modern JSON API (NJT's own docs list the host as `raildata.njt.gov`, which does not resolve; `.njtransit.com` is the real one). Auth is real username/password → 24h token, cached and reused rather than re-minted per call. NJT's feed gives a *scheduled* departure time plus a separate delay-in-seconds field (`SEC_LATE`, which can be negative for an early train) — the two must be added together to get a real predicted time, unlike MTA/PATH which report one absolute prediction directly. 172 rail stations (`assets/data/njt_rail_stations.csv`, built from NJT's own static GTFS feed via `backend/scripts/build_njt_rail_stations.py`) bundled into the unified search/favorites list. Because NJT rail requires a real credential (unlike MTA/PATH, which are public/unauthenticated), the credentials live server-side only — the Flutter app calls our own hosted backend (`GET /transit/njt-rail/{station_code}`) rather than NJT's API directly, so nothing extractable from the APK.
- **NJ Transit bus — real-time, live end-to-end** (`backend/app/transit/njt_bus.py`, `lib/njt/njt_bus_*.dart`) — initially assumed schedule-only (the first documented endpoint, `BUSDV2/getBusRoutes`, is static-only), but NJT's actual bus real-time API turned out to be a *different* one (`GTFSG2`), standard GTFS-realtime protobuf — the same format MTA already uses, and the same `gtfs_realtime_bindings` dependency. Real quirk: NJT's bus feed reports an empty `route_id` on every update, so the backend joins each update's `trip_id` against a bundled static lookup (`app/data/njt_bus_trip_routes.csv`, ~46k rows, built from NJT's static bus GTFS) to know which line an arrival belongs to. Scoped to a NYC-metro "core" bounding box (~5,100 stops, Hudson/Essex/Union/Bergen counties, roughly) rather than NJT's full statewide ~17k-stop network, per the PRD's NYC-metro-only scope decision — also excludes ~129 Newark Light Rail stops that share the same source file but are a different transit mode. No official per-line colors exist in NJT's bus GTFS (unlike rail), so bus routes render in a single agency color rather than per-line. Same backend-proxy pattern as rail for credentials.
- **Backend hosting verified with a 3rd real external credential** — NJT rail/bus both needed real third-party credentials (username/password) proxied through the now-hosted backend (see the hosting entry above), confirming the "credentials live server-side, app never holds them" pattern generalizes cleanly beyond the LLM key.
- **Behavior AI — the foundation feature of the re-scoped Phase 3 plan** (`backend/app/behavior_engine.py`, `GET /behavior/me`) — deterministic aggregation over `Trip` history, no LLM: feed accuracy (predicted vs. actual arrival error), direction choice (which route/direction a user actually picks per station+time — what Commute AI reads), and timing buffer (how long before predicted arrival a user starts moving — what Schedule AI reads). Each signal needs 3+ samples for a given station/time-slot before returning anything, never a low-confidence guess. Added `Trip.left_at` (reportable via the existing `PATCH /trips/{id}/outcome`) since nothing previously captured when a user started moving.
- **Chat AI's stateless tier, backend and UI** (`backend/app/chat_ai.py`, `backend/app/station_index.py`, `POST /chat`, `lib/chat/`) — a real chat screen (new 4th bottom-nav tab, "Chat") that answers free-text transit questions ("what time's the next PATH train from Grove Street") using only real live arrival data, no account required — deliberately not nested under the Account tab, since it needs none of that tab's login gate. A new compact server-side station-name index (`backend/app/data/chat_station_index.csv`, ~5,900 rows, built by `backend/scripts/build_chat_station_index.py` from the same data the Flutter app already bundles) resolves a station name out of the question's free text — the one thing nothing else in the backend previously needed, since every other feature gets a station code from the client or from trip history, never from unstructured text. Refuses plainly (never guesses) when a question is out of scope (fares, crowding), when no station matches, or when a name genuinely collides between two or more real, different stations (e.g. "Hoboken" naming both a real PATH station and a real NJT rail station) — same never-guess principle as the recommendation engine. LLM phrasing only turns already-fetched real data into a sentence, with a deterministic template fallback, mirroring `llm_phrasing.py`'s pattern.
- **Native Android passive departure detection, feeding Behavior AI's timing-buffer signal** (`android/app/src/main/kotlin/com/commuteos/commuteos/ActivityTransitionPlugin.kt`, `lib/behavior/departure_detector.dart`) — detects a real still→walking/in_vehicle transition (Google Play Services' Activity Recognition Transition API, wrapped in ~140 lines of hand-written Kotlin since no currently-maintained Flutter plugin wraps this specific API correctly) and reports it as `Trip.left_at` with zero user interaction required, per explicit user direction that this signal "shouldn't have user interaction... movement of user should capture this in some logical way." No GPS/location permission involved — only the `ACTIVITY_RECOGNITION` runtime permission, pure activity classification. Deliberately foreground-only for this first version (tied to the app being open, not a persistent background service) since every researched approach has real background-reliability gaps (Doze mode, OEM battery managers) that this scope avoids rather than papers over.
- **Schedule AI — timing decisions, ahead of departure** (`backend/app/schedule_engine.py`, `backend/app/jobs/send_commute_notifications.py`, `.github/workflows/commute-notifications.yml`) — evolves the existing commute-notification job from a single fixed daily clock time (7:45 AM ET for everyone) into a real per-user timing decision, fired an hour ahead of each user's own learned departure hour (clustered from `Trip.start_time`, same noon-cutoff split `home_office_engine.py` already uses). Compares today's live predicted arrival against a new Behavior AI signal — `typical_arrival_times_for_user`, the average clock time this station's arrival has historically been predicted at — to get a real, honestly-derived minutes-late number rather than a guess, and phrases one of three severities: on schedule, really delayed (citing the real number), or no live data at all (delegating to the same route-ranking engine `/recommendations` uses for a real substitute, per the PRD's "Schedule AI delegates routing to Commute AI's engine" design). Runs hourly via GitHub Actions (tightened from once daily, but not tighter than an hour — GH Actions cron doesn't reliably honor sub-hour intervals under platform load) with a new `User.last_commute_notification_date` guard against notifying the same person twice in one day.
- **Commute AI — routing decisions, in the moment** (`backend/app/commute_engine.py`, `GET /commute/{agency}/{code}`, `lib/commute/`) — fires when the user opens a station's arrivals screen, ranks that STATION'S OWN real routes/directions (e.g. Journal Square PATH's ToNY vs ToNJ, or a subway station's N vs W — a different comparison than Schedule AI's home-vs-office one), and compares the winner against Behavior AI's inferred usual pick for that station/hour. A card appears automatically on the arrivals screen only when the backend actually has something to say — explicitly "take X instead of your usual Y" when they genuinely differ, otherwise a plain confirmation; no card at all (never a fabricated one) when there's no live data or no history yet, same as if the feature didn't exist. Extended Chat AI's compact station index (`build_chat_station_index.py`) so PATH stations now carry their two real direction keys the same way MTA stations already carry their subway routes — the one new piece of shared infrastructure this needed. Also made the PRD's "shared brain" claim structurally real: Schedule AI's disruption-substitute path now calls the same named `commute_engine.rank_best` entry point Commute AI's own ranking uses, instead of a parallel copy of the underlying scorer.
- **Chat AI's personalized tier — the last piece of the four-feature plan** (`backend/app/chat_ai.py`, `backend/app/core/deps.py`'s `get_current_user_optional`) — one endpoint (`POST /chat`) now serves both tiers; auth became optional rather than required, so a logged-in user's personal-sounding question ("what do I usually take from here") unlocks the personalized tier while a logged-out caller's experience is unchanged. The personalized path calls `commute_engine.recommend_for_station` — the exact same function Commute AI's own endpoint calls — phrased with the exact same `phrase_commute_recommendation`, which is what makes the PRD's "must give the same answer Commute AI would give in card form" requirement true by construction. A new test, `test_personalized_answer_matches_commute_ai_exactly`, proves this by calling both real pipelines side by side and asserting character-for-character identical output — the concrete satisfaction of Phase 3's exit criterion. Falls back to the stateless arrivals answer (never a refusal) when there's nothing to personalize yet (not logged in, or no history/live data). Caught a real, previously-latent bug while writing the first full-sentence personalized-question test: the ambiguity check compared a whole question against a station name for exact equality, which only ever "worked" because every prior test happened to pass a bare station name — fixed with the same whole-word-substring check `find_stations` already used.
- **LIRR (Long Island Rail Road) — real-time, live end-to-end** (`backend/app/transit/lirr.py`, `lib/lirr/`) — MTA-operated, and its real-time GTFS-RT feed turned out to be genuinely public and unauthenticated (`api-endpoint.mta.info/Dataservice/mtagtfsfeeds/lirr%2Fgtfs-lirr`, same infrastructure MTA subway already uses), so `LirrService` fetches it directly from the Flutter app — no backend proxy needed for browsing, unlike NJT rail/bus. Unlike subway or NJT rail, LIRR stations aren't tied to one line: Jamaica alone is served by 10 of the system's 13 branches, and trains terminate at one of 4 distinct terminals (Penn Station, Grand Central, Atlantic Terminal, Hunterspoint Avenue) — so every arrival carries a real destination headsign (from a bundled `trip_id → branch/headsign` lookup, ~2,143 rows) and reuses the same destination-grouping UI already built for PATH's multi-destination directions, rather than a flat NJT-rail-style list. 127 stations (`assets/data/lirr_stations.csv`, built from MTA's static LIRR GTFS via `backend/scripts/build_lirr_stations.py`). Real gotcha: the real-time feed matches on LIRR's internal numeric stop_id (e.g. `"102"` for Jamaica), not the 3-letter station code (`"JAM"`) used everywhere else in the app — `LirrStation` carries both. The backend also has its own full Python implementation (not just a thin proxy) so LIRR works as a recommendation-engine candidate and in the scheduled notification job, the same reason `mta.py` exists server-side alongside the app's own direct-fetching `MtaService`.

## Getting started

### Mobile app (Flutter)

```
flutter pub get
flutter run
```

Requires the Flutter SDK and Android SDK on PATH — see `flutter doctor` to verify your environment.

### Backend (FastAPI)

```
cd backend
python -m venv .venv
.venv\Scripts\pip install -e ".[dev]"
copy .env.example .env    # then edit DATABASE_URL/SECRET_KEY as needed
.venv\Scripts\python -m pytest        # run tests (SQLite, no Postgres needed)
.venv\Scripts\python -m alembic upgrade head   # requires a running local Postgres (see below)
.venv\Scripts\python -m uvicorn app.main:app --port 8001 --reload
```

Runs on **port 8001**, not FastAPI's usual 8000 default — this dev environment already has an unrelated project on 8000. Requires a local PostgreSQL instance with a `commuteos`/`commuteos` user and database (`CREATE USER commuteos WITH PASSWORD 'commuteos'; CREATE DATABASE commuteos OWNER commuteos;`), matching `DATABASE_URL` in `.env.example`. This is only needed for *local* backend development — the app itself now talks to a real hosted backend by default (see below), not localhost.

### Hosted backend

The backend is deployed on **Render's free tier** (`backend/render.yaml`: build/start commands, health check at `/health`, migrations run automatically via `alembic upgrade head` on every deploy), backed by a free **Neon** Postgres instance. The app's `apiBaseUrl` (`lib/account/api_config.dart`) points at the hosted URL — no more USB/`adb reverse` tunnel or "backend only runs on my laptop" requirement. Free-tier tradeoff: the Render service spins down after ~15 minutes of no traffic, so the first request after a while takes a few extra seconds to wake it back up. This uniquely affected NJT rail/bus (the only two agencies proxied through this backend — MTA/PATH/LIRR fetch directly from the app), which is why NJT specifically felt slow while other agencies didn't; mitigated by `.github/workflows/keep-alive.yml`, a scheduled ping to `/health` every 10 minutes so the service shouldn't go idle long enough to spin down during normal use. Env vars (`DATABASE_URL`, `SECRET_KEY`, `GROQ_API_KEY`, etc.) are set directly in Render's dashboard, never committed.

## Tech stack (per PRD)

- Mobile: Flutter
- Backend (Phase 2+): FastAPI + PostgreSQL
- AI (Phase 3+): LLM used only for phrasing structured decision-engine output into natural language, never for the decision itself
- Maps: MapLibre + OSM
- Data: GTFS-RT, isolated per-agency parsers so one feed breaking doesn't break the others
