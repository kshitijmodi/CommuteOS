# Open Questions & Pending Decisions

Running list of unresolved questions for CommuteOS. Ask "what's pending?" any time to get a current read.

## Unresolved

- [ ] **iOS timeline** — PRD specifies Android-first (Flutter). Is iOS ever in scope, or Android-only for the foreseeable future?
- [ ] **Backend hosting/infra** — Where does FastAPI + PostgreSQL run for Phase 2 long-term (local dev only, a cheap cloud host, something else)? Local Postgres now works for dev (see Resolved), but nothing is hosted anywhere durable yet.
- [ ] **NJ Transit developer registration** — PENDING APPROVAL (confirmed 2026-07-29): registered 2026-07-27; account exists but is disabled pending manual review (confirmed via NJ Transit's own "forgot password" response: "Your userid ... is disabled. If you have just created your account please wait for approval which can take a few days."). Nothing to do but wait — if it's not approved after ~1 week, contact passcomm@njtransit.com per that message. Blocks only the NJ Transit feed/parser specifically — MTA and PATH work continues in parallel. Follow up once login works to get API key/credentials and wire up the NJ Transit parser module.
- [ ] **PATH data source is unofficial and could break without notice** — There is no documented, public, Port-Authority-supported real-time API for PATH. We're using `https://www.panynj.gov/bin/portauthority/ridepath.json` — the same undocumented endpoint that powers PATH's own website widget, not a published developer API with any SLA. Alternatives considered and rejected: a community GTFS-realtime wrapper (`path.transitdata.nyc/gtfsrt`) sits two additional unmaintained layers removed from PATH's actual backend, with a documented open "API is down" issue on its upstream dependency — more failure points, not fewer. If the panynj.gov endpoint ever changes shape or disappears, `PathService` (lib/path/path_service.dart) is the single place to update; the rest of the app only depends on the agency-agnostic `TransitService` interface.
- [ ] **PATH static station data is hardcoded, not from a bundled file** — Unlike MTA's ~496 stations (parsed from a bundled CSV), PATH's 13 stations are hardcoded directly in `lib/path/path_station.dart` since there are so few and they essentially never change. If PATH ever adds/removes/renames a station, this needs a manual code update rather than a data refresh — acceptable tradeoff given PATH hasn't changed its station list in decades, but worth knowing if it ever surprises us.
- [ ] **Static station data refresh strategy** — `assets/data/mta_stations.csv` is a point-in-time snapshot bundled into the app. MTA updates this rarely, but when a station opens/closes/renames the app won't know until this asset is manually refreshed and the app rebuilt. Fine for now — worth revisiting if this becomes a real maintenance burden.
- [ ] **DEFERRED: minor real-device UI issues** (2026-07-29) — After moving Phase 1 testing from the emulator to a real sideloaded Pixel 8 Pro, user reports it's "much better" overall with only minor remaining issues, explicitly deferred rather than detailed yet. Revisit when the user is ready to enumerate them.
- [ ] **Mobile app's backend URL requires manual per-session setup** — `lib/account/api_config.dart` points at `http://localhost:8001`, reached via `adb reverse tcp:8001 tcp:8001` over USB (see Resolved entry on why USB instead of Wi-Fi). This means: (a) the phone must be plugged in via USB and the adb reverse command re-run every session for account/trip features to reach the backend — browsing/favorites are unaffected since those never call the backend; (b) this is obviously not a production config. Needs revisiting once "Backend hosting/infra" (above) is decided — at that point this becomes a real hosted URL.
- [ ] **NJ Transit real-time integration not implemented, only scaffolded** — `backend/app/transit/njt.py` exists but raises `NotImplementedError`. Research surfaced real uncertainty about the actual wire format (rail real-time is legacy SOAP/XML, not GTFS-RT protobuf like MTA; bus format unconfirmed; auth is username+password, possibly with a token layer, not a simple API key) — deliberately not guessed at. Once the developer account is approved: get real credentials, make one real request, inspect the actual response shape, then write the parser the same way MTA/PATH were each verified against live data first.
- [ ] **Groq API key not yet added** — `backend/app/llm_phrasing.py` is built and tested against the template fallback, but the user's actual Groq key hasn't been added to `.env` yet, so real LLM-phrased recommendations haven't been verified, only the deterministic fallback path. Add `GROQ_API_KEY` to `backend/.env` and test a real call once ready.
- [ ] **Decision engine's "confidence" is a scoped-down stand-in for the PRD's "recent delay variance"** — the PRD's formula is `predicted_arrival_time − (reliability_weight × recent_delay_variance)`, which needs historical predicted-vs-actual deltas across many past trips per route/station. Current trip data doesn't have that volume/shape yet (Phase 2 is brand new), so `backend/app/decision_engine.py` uses live-vs-stale feed status as a proxy for trustworthiness instead. Documented clearly in the module docstring so it's not mistaken for the full PRD formula — revisit once enough real recommendation-outcome data exists (`GET /trips/accuracy` is already tracking toward this).
- [ ] **Recommendation candidates are hand-picked by the user, not auto-discovered** — `POST /recommendations` scores whatever candidate routes the client sends it; there's no "given my home and office, what are my real options" discovery yet (that would need the PRD's home/office-location inference, which isn't built). The Flutter recommendation screen works around this by letting the user pick 2+ of their own favorited stations to compare — functional for a demo, but not the fully proactive experience the PRD describes.
- [ ] **`transfer_aversion_score` cannot be computed from real data yet** — same root cause as the decision-engine stand-in above: the PRD's signal needs "user was shown both a direct and transfer route and picked one," which doesn't exist anywhere in the data model (no route-planning/alternative-route logging). Stays at its neutral default (0.5) rather than a fabricated number. Would need a real route-comparison feature to fix properly.
- [ ] **Full rapid-build round is untested against real usage** — all of Phase 2 and Phase 3 were built and unit/integration tested in one sitting per the user's explicit request ("develop everything remaining rapidly... once all features are built, we'll solve issues, then do designing"). This means: no real 2-week trip history exists (only the synthetic seed script), the recommendation screen/preferences screen haven't been tried on the actual phone yet, and the LLM phrasing path is untested against a real Groq call. Treat "built" and "works for a real user" as different claims until manually exercised.

## Resolved

- [x] **Flutter/Android dev toolchain** (resolved 2026-07-28) — JDK 17, Flutter SDK 3.44.8 (stable), Android Studio + SDK (cmdline-tools, platform-tools, build-tools 36.0.0), Windows long path support, and Android SDK licenses are all installed/accepted. `flutter doctor` clean except Visual Studio (Windows desktop dev), which is irrelevant since we're targeting Android only.
- [x] **Repo hosting** (resolved 2026-07-28) — Public GitHub repo created at github.com/kshitijmodi/CommuteOS, initial Flutter scaffold committed and pushed. Note: `CommuteOS/` was previously a subfolder inside a git repo rooted at the whole Downloads folder (mixed with unrelated personal files) — it now has its own independent `.git`, unaffected by that parent repo.
- [x] **MTA GTFS-RT integration** (resolved 2026-07-28) — Confirmed MTA subway feeds are public/unauthenticated (no API key needed, unlike some outdated docs suggest). Built `lib/mta/` (feed URLs, protobuf parsing via `gtfs_realtime_bindings`, a live-arrivals screen) and verified against the real feed on an Android emulator (`commuteos_test` AVD, API 35). Uses the base GTFS-RT spec only — not MTA's NYCT-specific proto extension (train assigned/unassigned status) — which is sufficient for Phase 1's basic arrival-time display.
- [x] **All-station search + correctness bug caught** (resolved 2026-07-28) — Initial hardcoded-station build used a wrong stop_id (`R16N`, which is actually Times Sq, not Union Square as labeled) — the pipeline worked but showed the wrong station's data under the wrong label. Fixed by building real station data support: bundled MTA's `Stations.csv` (496 stations, pre-joined with routes and direction labels) as a local asset, parsed via the `csv` package, added a route→realtime-feed lookup table (not derivable from static GTFS, hardcoded ~30 entries), and rebuilt the home screen as a searchable station list. Verified multiple stations and both direction tabs against live data on the emulator.
- [x] **Favorites design** (resolved 2026-07-28) — Whole-station favorites (not per-direction), persisted locally via `shared_preferences` (no account/backend in Phase 1). Favorites is now the app's home screen with an empty state prompting a first search; full station search is reachable via a search icon in the app bar. Star toggle is a shared widget (`StationListTile`) used in both the favorites view and search screen so they can't drift out of sync. Caught and fixed a real test-authoring bug along the way: `pumpAndSettle()` hangs forever against a `CircularProgressIndicator`'s implicit animation, and separately, `rootBundle.loadString` (asset loading) uses real async I/O that the test framework's fake clock doesn't advance — needed `tester.runAsync()` to let it resolve for real before pumping again.
- [x] **Station list ordering + duplicate rows** (resolved 2026-07-29) — Two bugs reported by user after using the search list: (1) plain string sort put "111 St" before "2 Av" (numeric-as-string ordering); (2) station names like "Canal St" appeared as multiple separate rows (MTA's Stations.csv genuinely has multiple rows per name — some are different platforms of one connected complex sharing a `Complex ID`, some are entirely separate unconnected stations that just happen to share a name, e.g. two distinct "86 St"s). Fixed: added `compareStationNames()` (numeric-aware natural sort, numbers before letters, per user's explicit preference) and a `StationGroup` model that groups all `MtaStation`s sharing a name into one list row; tapping a row with more than one station opens a picker sheet (listing each option's routes/borough) instead of guessing or duplicating rows. Favorites screen intentionally does NOT re-group — a favorited station was already disambiguated when the user picked it, so it shows as its own row even if another station elsewhere shares its name.
- [x] **PATH integration + cross-agency refactor** (resolved 2026-07-29) — Added PATH real-time arrivals (13 stations) via the undocumented `panynj.gov/bin/portauthority/ridepath.json` endpoint (see the unresolved item above for the sourcing risk). Before writing PATH-specific code, did a full refactor to a proper cross-agency abstraction (`lib/transit/transit_models.dart`: `TransitStation`/`TransitService`/`TransitArrival`/`TransitArrivalsResult`) since the user wanted MTA and PATH stations merged into one unified search/favorites list rather than kept in separate sections — this touched most existing screens (`arrivals_screen.dart`, `station_search_screen.dart`, `station_list_tile.dart`, `station_group.dart`, `station_picker_sheet.dart`, `natural_sort.dart` all moved from `lib/mta/` to `lib/transit/` since they're no longer MTA-specific) but avoids a second rework when NJ Transit is added later. `FavoritesRepository` keys are now namespaced per-agency (`mta:R20`, `path:JSQ`) to guard against a future cross-agency ID collision (none exist today, verified). PATH's feed includes explicit staleness detection (`isLive` flag, checked against the feed's own `lastUpdated` timestamps, >5min old = flagged) per the PRD's graceful-degradation requirement for PATH specifically. Caught and fixed a real bug while hardcoding PATH's 13 stations: Hoboken's code was mistyped with Cyrillic "Н"/"О" instead of Latin "H"/"O" (visually identical, would have silently failed all lookups against the real feed) — worth remembering that any hand-typed station-code table deserves an ASCII/encoding sanity check.
- [x] **PATH trains missing from 33 St (and 14 St/23 St) station rows** (resolved 2026-07-29) — User reported PATH arrivals didn't show when tapping "33 St". Root cause: `PathStation.all` used ordinal-suffixed names ("14th St", "23rd St", "33rd St") that didn't exactly match MTA's plain station names ("14 St", "23 St", "33 St"), so `StationGroup.groupByName`'s exact-name match never merged them — two separate list rows for what's the same accessible physical location, and whichever row you tapped only showed that one agency's trains. Fixed by renaming the three PATH stations to match MTA's exact naming convention (verified against MTA's Stations.csv there's no unintended collision introduced). Added a regression test (`station_group_test.dart`) asserting a PATH station and its MTA counterpart merge into one group with both agencies' routes present, so this can't silently regress if either agency's station list is edited again.
- [x] **Geographic scope** (resolved 2026-07-29) — NYC-metro only for the foreseeable future, per the PRD's own framing (other metros are explicitly a Phase 4+ consequence, not something to design toward now). No architectural changes needed — current per-agency isolation (lib/mta/, lib/path/) already doesn't assume a single metro area, it just isn't being generalized further than needed today.
- [x] **User model for Phase 2+** (resolved 2026-07-29) — Multi-user product with real accounts/auth starting in Phase 2, not a single-user personal tool. This means Phase 2's `users` table needs real per-user data isolation and an actual signup/login flow (not just a single preference row), and auth/session security becomes in-scope work for that phase rather than skippable. Worth flagging when Phase 2 planning starts: this is meaningfully more scope than a personal-tool build would have been.
- [x] **Phase 2 backend scaffolded** (resolved 2026-07-29) — FastAPI + SQLAlchemy 2.0 + Alembic under `backend/`, matching the PRD's schema (`users`, `trips`, `preferences`) plus real auth per the multi-user decision above: bcrypt-hashed passwords, JWT access tokens, `/auth/signup`, `/auth/login`, `/users/me`. Every signup immediately gets a `preferences` row at PRD-specified defaults. 8 tests passing against in-memory SQLite (no Postgres-specific features exercised, so this doesn't validate against Postgres yet). Caught and fixed a real dependency-compatibility bug: `bcrypt` 5.0 (latest) removed an attribute `passlib` 1.7.x's bcrypt backend still expects (`__about__`), and separately trips passlib's internal self-test with a "password too long" error during its own wrap-bug detection — pinned `bcrypt<4.1` as the fix. The Alembic migration itself is hand-written (not autogenerated, since that requires a live DB connection) and only syntax-checked, not yet run against real Postgres — see the Postgres-install item above.
- [x] **Auth UX + trip-logging trigger** (resolved 2026-07-29) — Two decisions made together when wiring the app to the new backend: (1) browsing/favoriting stays completely login-free — an account is opt-in, reachable via an account icon on the favorites screen, not a gate in front of the whole app; (2) trip logging happens automatically whenever a *logged-in* user opens any station's arrivals screen (no explicit "start commute" button), matching the PRD's framing that usage itself is the signal. Anonymous (logged-out) usage sends nothing to the backend — no anonymous-account creation/migration complexity, at the cost of losing any pre-signup usage history for that user. Built `lib/account/` (AuthRepository, TripLogger, AccountScreen) plus a backend `POST /trips` endpoint; `dest_stop` is nullable and left null for now since the app only knows which station was viewed, not a real destination (no route-planning feature exists yet) — never guess/duplicate origin_stop into it. 12 new tests total (4 backend trip tests, 8 Flutter tests for AuthRepository/TripLogger via mocked HTTP).
- [x] **PostgreSQL installed and verified end-to-end from the real phone** (resolved 2026-07-30/31) — Installed via `winget install --id PostgreSQL.PostgreSQL.17` (needed the user to approve the UAC prompt in their own elevated terminal). Since the user never set a postgres superuser password during install, had to temporarily flip `pg_hba.conf`'s local/host auth method from `scram-sha-256` to `trust` (user edited the file as Administrator + restarted the `postgresql-x64-17` service — editing this file and restarting the service both require admin rights the agent doesn't have), used that brief trust window to set a real postgres password and create the `commuteos` user/database matching the backend's `DATABASE_URL`, then had the user revert `pg_hba.conf` back to `scram-sha-256` and restart again — verified real password auth was actually re-enforced (not just cosmetically reverted) before proceeding. Ran `alembic upgrade head` for real for the first time; all three tables (`users`, `trips`, `preferences`) created correctly matching the SQLAlchemy models. Generated a real random `SECRET_KEY` for `backend/.env` (gitignored, not committed) rather than leaving the insecure dev default in use.

  Getting the phone to actually reach the backend took two more rounds: first, the app's Wi-Fi-IP approach (`192.168.1.19:8000`) was blocked by this dev laptop's firewall/managed-security software even after adding an explicit allow rule — switched to USB-based `adb reverse tcp:8000 tcp:8000` instead, which tunnels the phone's own `localhost:8000` to the laptop's real `localhost:8000` and sidesteps the network/firewall question entirely. Second, port 8000 turned out to already be occupied by a *different, unrelated* Python project of the user's (a personal finance tracker with `/investments`, `/plaid`, `/teller` routes) that had been running since earlier that day — confirmed by inspecting the actual `/openapi.json` being served, not just assuming a bind failure. Rather than touch the user's other app, moved CommuteOS to port 8001 (`adb reverse tcp:8001 tcp:8001`, `uvicorn --port 8001`, `api_config.dart` updated to match). Verified genuinely end-to-end through the real app UI (not curl): signed up via the account screen on the physical Pixel 8 Pro, opened a PATH station's arrivals screen, and confirmed via direct `psql` query that both the user row and a trip row (`mode: path, origin_stop: EXP, dest_stop: null`) landed correctly in Postgres.
- [x] **Phase 2 + Phase 3 fully built in one rapid-build round** (resolved 2026-07-31) — Per explicit user direction to build all remaining phases rapidly before testing/design passes. **Phase 2**: `preference_engine.py` recomputes `walking_tolerance_m` from trip history via a distinct-stops-used proxy (documented as a scoped-down stand-in for the PRD's real "distance before choosing a farther station" signal, since station-distance data doesn't exist yet); `transfer_aversion_score` deliberately left at its neutral default rather than faked, since its real signal doesn't exist in the data model either. `seed_demo_trips.py` generates ~3 weeks of realistic synthetic weekday-commute trips so the feature is demoable without real usage history. **Phase 3**: ported MTA (protobuf) and PATH (JSON) live-fetching to Python (`backend/app/transit/`), verified against real live feeds, so the backend can score routes itself per the PRD's architecture (decided explicitly over having the Flutter app POST pre-fetched data, to keep `/recommendations` self-contained and demoable via curl alone). `decision_engine.py` is deterministic (PRD requirement — no LLM in the scoring path), weighted by the user's `reliability_pref`; its "confidence" signal is a documented stand-in for "recent delay variance" (see the unresolved item above — not enough trip-outcome data exists yet for the real formula). `llm_phrasing.py` uses Groq's OpenAI-compatible API (user has a Groq key, to be added later) for phrasing only, with a deterministic template fallback when no key is configured — verified via the fallback path only, not a real Groq call yet. `POST /recommendations`, `PATCH /trips/{id}/outcome`, `GET /trips/accuracy` implement the PRD's trust-preserving design end-to-end. **NJ Transit**: scaffolded (`njt.py`) but deliberately raises `NotImplementedError` rather than guessing a wire format, since research surfaced genuine uncertainty (legacy SOAP/XML for rail, unconfirmed for bus) that shouldn't be papered over until real credentials arrive. Flutter: new `PreferencesScreen` ("What CommuteOS has learned") and `RecommendationScreen` ("What should I take?", pick 2+ favorites to compare), both reachable from the account screen. 40 backend tests + 23 Flutter tests passing, both analyzers clean — but see the unresolved item above on this being unit/integration-tested only, not yet exercised against real usage or a real LLM call.
