# Open Questions & Pending Decisions

Running list of unresolved questions for CommuteOS. Ask "what's pending?" any time to get a current read.

## Unresolved

- [ ] **iOS timeline** — PRD specifies Android-first (Flutter). Is iOS ever in scope, or Android-only for the foreseeable future?
- [x] **Backend hosting/infra** (resolved 2026-08-01) — FastAPI hosted on Render's free tier, Postgres on Neon's free tier. See the new Resolved entry below for details.
- [ ] **PATH data source is unofficial and could break without notice** — There is no documented, public, Port-Authority-supported real-time API for PATH. We're using `https://www.panynj.gov/bin/portauthority/ridepath.json` — the same undocumented endpoint that powers PATH's own website widget, not a published developer API with any SLA. Alternatives considered and rejected: a community GTFS-realtime wrapper (`path.transitdata.nyc/gtfsrt`) sits two additional unmaintained layers removed from PATH's actual backend, with a documented open "API is down" issue on its upstream dependency — more failure points, not fewer. If the panynj.gov endpoint ever changes shape or disappears, `PathService` (lib/path/path_service.dart) is the single place to update; the rest of the app only depends on the agency-agnostic `TransitService` interface.
- [ ] **PATH static station data is hardcoded, not from a bundled file** — Unlike MTA's ~496 stations (parsed from a bundled CSV), PATH's 13 stations are hardcoded directly in `lib/path/path_station.dart` since there are so few and they essentially never change. If PATH ever adds/removes/renames a station, this needs a manual code update rather than a data refresh — acceptable tradeoff given PATH hasn't changed its station list in decades, but worth knowing if it ever surprises us.
- [ ] **Static station data refresh strategy** — `assets/data/mta_stations.csv` is a point-in-time snapshot bundled into the app. MTA updates this rarely, but when a station opens/closes/renames the app won't know until this asset is manually refreshed and the app rebuilt. Fine for now — worth revisiting if this becomes a real maintenance burden.
- [ ] **DEFERRED: minor real-device UI issues** (2026-07-29) — After moving Phase 1 testing from the emulator to a real sideloaded Pixel 8 Pro, user reports it's "much better" overall with only minor remaining issues, explicitly deferred rather than detailed yet. Revisit when the user is ready to enumerate them.
- [x] **Mobile app's backend URL requires manual per-session setup** (resolved 2026-08-01) — Fixed by the hosting work above; `apiBaseUrl` now points at the real hosted Render URL. No more USB/`adb reverse` requirement for account/trip/recommendation features.
- [ ] **NJ Transit real-time integration not implemented, only scaffolded** — `backend/app/transit/njt.py` exists but raises `NotImplementedError`. Developer account approval **came through 2026-08-01** (BUSDATA, GTFS-BUS, GTFS-RAIL, RailData subscriptions active) — no longer blocked on approval, this is now purely an implementation task. Research prior to approval surfaced real uncertainty about the actual wire format (rail real-time is legacy SOAP/XML, not GTFS-RT protobuf like MTA; bus format unconfirmed; auth is username+password, possibly with a token layer, not a simple API key) — deliberately not guessed at; next step is making one real request with the actual credentials, inspecting the actual response shape, then writing the parser the same way MTA/PATH were each verified against live data first.
- [ ] **Decision engine's "confidence" is a scoped-down stand-in for the PRD's "recent delay variance"** — the PRD's formula is `predicted_arrival_time − (reliability_weight × recent_delay_variance)`, which needs historical predicted-vs-actual deltas across many past trips per route/station. Current trip data doesn't have that volume/shape yet (Phase 2 is brand new), so `backend/app/decision_engine.py` uses live-vs-stale feed status as a proxy for trustworthiness instead. Documented clearly in the module docstring so it's not mistaken for the full PRD formula — revisit once enough real recommendation-outcome data exists (`GET /trips/accuracy` is already tracking toward this).
- [ ] **Recommendation candidates are hand-picked by the user, not auto-discovered** — `POST /recommendations` scores whatever candidate routes the client sends it; there's no "given my home and office, what are my real options" discovery yet (that would need the PRD's home/office-location inference, which isn't built). The Flutter recommendation screen works around this by letting the user pick 2+ of their own favorited stations to compare — functional for a demo, but not the fully proactive experience the PRD describes.
- [ ] **`transfer_aversion_score` cannot be computed from real data yet** — same root cause as the decision-engine stand-in above: the PRD's signal needs "user was shown both a direct and transfer route and picked one," which doesn't exist anywhere in the data model (no route-planning/alternative-route logging). Stays at its neutral default (0.5) rather than a fabricated number. Would need a real route-comparison feature to fix properly.
- [ ] **Full rapid-build round is untested against real usage** — all of Phase 2 and Phase 3 were built and unit/integration tested in one sitting per the user's explicit request ("develop everything remaining rapidly... once all features are built, we'll solve issues, then do designing"). This means: no real 2-week trip history exists (only the synthetic seed script), and the recommendation screen/preferences screen haven't been tried on the actual phone yet. Treat "built" and "works for a real user" as different claims until manually exercised. (LLM phrasing itself IS now verified against a real Groq call — see Resolved.)
- [ ] **Daily reminder notification is local-only, not condition-aware** — `commute_notification_service.dart` fires a fixed 7:45 AM local notification once enabled; it can't check live transit conditions before firing (e.g. skip the notification, or change its wording, if there's no delay) since that would need a server-side scheduled job plus real push (see the hosting/infra item above). Tapping the notification just opens the app — live conditions are only ever checked there. Revisit once there's a hosting story.
- [ ] **Exact-alarm permission behavior unverified on real Android 12+ restrictions** — `SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM` are declared and `androidScheduleMode: exactAllowWhileIdle` is used, but this hasn't been exercised on the real Pixel 8 Pro yet (only `flutter analyze`-clean and unit-testable paths were checked). Android can silently revoke exact-alarm permission for battery reasons on some OEM skins; if the daily reminder is ever reported as "not firing," check `adb shell dumpsys alarm` and the app's exact-alarm permission toggle in system settings before assuming a code bug.
- [ ] **Home/office inference needs 3+ trips per time slot before showing anything** — a brand-new account (or the synthetic demo seed, if its trip count per slot is ever reduced) may show no home/office card at all rather than a wrong guess. This is intentional (see Resolved entry), but worth remembering if the card unexpectedly doesn't appear during a demo — check trip counts before assuming a bug.
- [ ] **MTA route-color table needs a periodic sanity check against NYCT's actual branding** — `_mtaRouteColors` in `lib/design/components.dart` is a hand-maintained lookup, not derived from a live source (MTA's GTFS static feed's `routes.txt` has an authoritative `route_color` column, but pulling that in was more machinery than a ~30-entry table that essentially never changes is worth right now). If MTA ever rebrands a line's color, or a route ID is missing from the table, that route silently falls back to the generic agency badge color rather than erroring — worth a periodic glance if a route's color ever looks wrong.
- [ ] **New dark theme + bottom nav not yet visually verified on the real Pixel 8 Pro** — the phone wasn't plugged in via USB during this design pass. Verified instead via `flutter analyze` (clean), `flutter test` (23/23 passing, one test's expected empty-state copy updated to match the new `EmptyState` component's title-without-period convention), and `flutter build apk --debug` (succeeds — this is what caught the desugaring bug below). None of that confirms real-device rendering: actual contrast/legibility in daylight, tap-target sizing on a real screen, bottom-nav gesture-nav interaction on Android, and the new `PopScope`-driven back-button behavior in `root_shell.dart` (pop the active tab's inner Navigator before exiting the app) all still need a real run-through. Do this before treating the design pass as done, not just shipped.
- [ ] **`flutter_local_notifications` silently required Android core library desugaring** — discovered only now, via a real `flutter build apk` (the home/office round that added this dependency had only run `flutter analyze`/`flutter test`, neither of which invokes Gradle, so a real build was never attempted until this design pass). Fixed by enabling `isCoreLibraryDesugaringEnabled` and adding the `desugar_jdk_libs` dependency in `android/app/build.gradle.kts`. Worth remembering: analyzer-clean and tests-passing is not the same guarantee as "the app actually builds" for native-plugin-heavy changes — a real `flutter build apk --debug` should be part of verifying any round that touches Android-side plugin config, not just Dart-analyzable changes.
