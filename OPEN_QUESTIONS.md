# Open Questions & Pending Decisions

Running list of unresolved questions for CommuteOS. Ask "what's pending?" any time to get a current read.

## Unresolved

- [ ] **iOS timeline** — PRD specifies Android-first (Flutter). Is iOS ever in scope, or Android-only for the foreseeable future?
- [x] **Backend hosting/infra** (resolved 2026-08-01) — FastAPI hosted on Render's free tier, Postgres on Neon's free tier. See the new Resolved entry below for details.
- [ ] **PATH data source is unofficial and could break without notice** — There is no documented, public, Port-Authority-supported real-time API for PATH. We're using `https://www.panynj.gov/bin/portauthority/ridepath.json` — the same undocumented endpoint that powers PATH's own website widget, not a published developer API with any SLA. Alternatives considered and rejected: a community GTFS-realtime wrapper (`path.transitdata.nyc/gtfsrt`) sits two additional unmaintained layers removed from PATH's actual backend, with a documented open "API is down" issue on its upstream dependency — more failure points, not fewer. If the panynj.gov endpoint ever changes shape or disappears, `PathService` (lib/path/path_service.dart) is the single place to update; the rest of the app only depends on the agency-agnostic `TransitService` interface.
- [ ] **PATH static station data is hardcoded, not from a bundled file** — Unlike MTA's ~496 stations (parsed from a bundled CSV), PATH's 13 stations are hardcoded directly in `lib/path/path_station.dart` since there are so few and they essentially never change. If PATH ever adds/removes/renames a station, this needs a manual code update rather than a data refresh — acceptable tradeoff given PATH hasn't changed its station list in decades, but worth knowing if it ever surprises us.
- [ ] **Static station data refresh strategy** — `assets/data/mta_stations.csv` is a point-in-time snapshot bundled into the app. MTA updates this rarely, but when a station opens/closes/renames the app won't know until this asset is manually refreshed and the app rebuilt. Fine for now — worth revisiting if this becomes a real maintenance burden.
- [ ] **DEFERRED: minor real-device UI issues** (2026-07-29) — After moving Phase 1 testing from the emulator to a real sideloaded Pixel 8 Pro, user reports it's "much better" overall with only minor remaining issues, explicitly deferred rather than detailed yet. Revisit when the user is ready to enumerate them.
- [x] **Mobile app's backend URL requires manual per-session setup** (resolved 2026-08-01) — Fixed by the hosting work above; `apiBaseUrl` now points at the real hosted Render URL. No more USB/`adb reverse` requirement for account/trip/recommendation features.
- [x] **NJ Transit rail + bus real-time integration** (resolved 2026-08-02) — See the new Resolved entry below for the full story (both are live, tested, and wired into the app end-to-end).
- [ ] **NJT bus stops limited to a NYC-metro "core" bounding box** — `backend/scripts/build_njt_bus_stops.py` filters NJT's full ~17k-stop statewide bus network down to ~5,100 stops in a hand-picked lat/lng box (roughly Hudson/Essex/Union/Bergen counties), matching the PRD's NYC-metro-only scope. This is a rough rectangle, not real county boundaries — a stop just outside the box (e.g. parts of Middlesex or further south) won't appear in search/favorites even if it's arguably still "NYC-metro." Revisit the box's exact edges if a real user hits a missing stop they'd expect to find.
- [ ] **NJT bus/rail trip-to-route and station data are static snapshots, same tradeoff as MTA's CSV** — `assets/data/njt_rail_stations.csv`, `assets/data/njt_bus_stops.csv`, and the backend-only `app/data/njt_bus_trip_routes.csv` are all built once from NJT's static GTFS feeds (`backend/scripts/build_njt_*.py`) and bundled/committed, not fetched live. If NJT adds/removes a station or stop, or reshuffles bus trip_ids in a schedule change, these go stale until manually rebuilt and redeployed. Same accepted tradeoff as MTA's station CSV — worth knowing if a specific stop/line ever looks wrong.
- [ ] **NJT rail/bus not yet exercised on the real phone** — built and verified against the real live APIs from a dev machine (real signup, real tokens, real arrivals data cross-checked against NJT's own feed), and Flutter analyzer/tests are clean, but the actual app hasn't been run on the physical Pixel 8 Pro with these features yet. Bundled the largest single asset addition to date (~325KB bus stops CSV) — worth confirming app install size and station-list scroll performance feel fine on a real device.
- [ ] **Decision engine's "confidence" is a scoped-down stand-in for the PRD's "recent delay variance"** — the PRD's formula is `predicted_arrival_time − (reliability_weight × recent_delay_variance)`, which needs historical predicted-vs-actual deltas across many past trips per route/station. Current trip data doesn't have that volume/shape yet (Phase 2 is brand new), so `backend/app/decision_engine.py` uses live-vs-stale feed status as a proxy for trustworthiness instead. Documented clearly in the module docstring so it's not mistaken for the full PRD formula — revisit once enough real recommendation-outcome data exists (`GET /trips/accuracy` is already tracking toward this).
- [ ] **`POST /recommendations` (the on-demand, user-picked screen) still requires manually selecting 2+ favorites** — the new auto-discovery via home/office inference (see the commute-notification Resolved entry) only feeds the *proactive* notification pipeline, not the Flutter "What should I take?" screen itself, which still works exactly as before. Wiring that screen to also default to "your home/office options" instead of requiring manual favorite-picking is a real remaining gap, now that `CandidateSpec`-building from home/office exists in `send_commute_notifications.py` and could be reused there.
- [ ] **`transfer_aversion_score` cannot be computed from real data yet** — same root cause as the decision-engine stand-in above: the PRD's signal needs "user was shown both a direct and transfer route and picked one," which doesn't exist anywhere in the data model (no route-planning/alternative-route logging). Stays at its neutral default (0.5) rather than a fabricated number. Would need a real route-comparison feature to fix properly.

- [ ] **MTA/PATH auto-notifications only work once a route/direction has actually been captured from browsing** — the notification job needs `User.home_route_or_direction`/`office_route_or_direction`, which is only set the first time `ArrivalsScreen` successfully loads real arrivals for that exact station after this round shipped (see the Resolved entry below). This is intentional (see Resolved entry), but worth remembering if the card unexpectedly doesn't appear during a demo — check trip counts before assuming a bug.

If MTA ever rebrands a line's color, or a route ID is missing from the table, that route silently falls back to the generic agency badge color rather than erroring — worth a periodic glance if a route's color ever looks wrong.

Do this before treating the design pass as done, not just shipped.
- [ ] **`flutter_local_notifications` silently required Android core library desugaring** — discovered only now, via a real `flutter build apk` (the home/office round that added this dependency had only run `flutter analyze`/`flutter test`, neither of which invokes Gradle, so a real build was never attempted until this design pass). Worth remembering: analyzer-clean and tests-passing is not the same guarantee as "the app actually builds" for native-plugin-heavy changes — a real `flutter build apk --debug` should be part of verifying any round that touches Android-side plugin config, not just Dart-analyzable changes.
