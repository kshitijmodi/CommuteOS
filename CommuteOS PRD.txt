# PRD: AI CommuteOS — Personal Mobility Agent

## 1. Vision
Not a transit app. A personal mobility decision engine — an AI layer that sits on top of transit, walking, driving, and eventually flight data, and answers one question continuously: "Given who this person is and what's happening right now, what should they do?"

Transit is the first domain because it has the highest-frequency decision points (twice a day, every day) and the richest signal to learn from. But the architecture — preference model + real-time inputs + decision engine + natural-language delivery — is domain-agnostic by design, so "expand to driving/flights/bike share" isn't a roadmap slide, it's a consequence of how Phase 2 is built.

One-liner (resume/pitch deck): Built an AI mobility agent that learns a commuter's routing preferences and reliability tolerance, then proactively recommends real-time travel decisions across transit modes — not just displays transit data.

## 2. Problem Statement
Transit apps are stateless. Every session starts from zero — they don't know this is your 47th Tuesday taking the 8:15 from Grove Street, or that you'd rather stand on a slower, more reliable train than gamble on a faster one that's delayed twice a week. The decision-making work is done by the human, every single day, from raw data. That's the gap.

## 3. Target User & Core Use Case
Primary persona: the routine commuter with a real choice between modes — someone who could take PATH or NJ Transit or a bus, where the "best" option changes day to day based on delays. This is a better initial persona than "any transit rider," because a single-mode rider doesn't need a decision engine, just a notification engine.

Secondary persona (Phase 3+): the person whose day has variable end times (meetings, appointments) where "when should I leave" depends on calendar data, not just fixed schedule.

## 4. Success Metrics
Product metrics (what you'd track with real users): daily active decision-taken rate, recommendation accuracy (predicted vs. actual arrival delta), retention at day 7/30.

Portfolio metrics (what matters now): a working demo with real personalization logic visible, a clean PRD/README, and a defensible answer to "how is this different from Transit App or Google Maps."

## 5. Differentiation
Existing apps optimize route-finding. AI CommuteOS optimizes a specific person's utility function — a weighted blend of speed, reliability, walking tolerance, and transfer aversion that the app estimates from behavior rather than asking the user to configure it upfront.

The moat isn't "AI" — it's the fitted per-user preference model plus the outcome-tracking loop that keeps improving it. "Memory" alone is what Transit App's saved-routes feature already does.

## 6. Phased Build

### Phase 1 — Real-Time Multi-Agency Transit Intelligence
Goal: A working, shippable Android app with zero backend. Credibility layer — it has to just work before AI gets layered on.

Features:
- Live MTA subway arrivals (GTFS-RT, public and stable)
- Live NJ Transit updates (requires developer registration — apply week 1, longest lead-time item)
- PATH arrivals — treat as beta tier given feed reliability risk; fallback to scheduled times with a "live data unavailable" flag rather than showing stale data as live
- Bus tracking, service alerts, interactive map (MapLibre + OSM)
- Favorite stations/routes (local device storage only — not the personalization layer, just a shortcut list)

Explicit non-goal: no recommendations, no "you should." Phase 1 only answers "what exists right now" — its job is to prove the data pipeline works and start generating usage data for Phase 2.

Architecture:
Android App (Flutter) -> GTFS-RT parsers (per agency, isolated — one agency's feed breaking shouldn't break the others) -> MTA (public) | NJ Transit (registered API) | PATH (community feed, degrade gracefully)

Exit criteria: you personally use it daily on your own commute for two weeks without opening the MTA/NJ Transit apps instead.

### Phase 2 — Personal Commute Memory
Goal: Move from "app that shows data" to "app that has a model of you."

Learned signals:
- Home/office location — inferred from most common start/end points over ~5 trips, confirmed once via a simple prompt
- Typical departure time — rolling median of actual app-open/trip-start times per weekday, inferred
- Walking tolerance — distance the user accepts before usage data shows they picked a farther/less-crowded station, inferred
- Reliability vs. speed preference — needs a lightweight explicit input (single onboarding slider: "arrive on time" vs. "arrive fastest") since the tradeoff is rarely observable naturally; refined over time with observed choices
- Transfer aversion — frequency of choosing a direct-but-slower route over a faster-with-transfer route, when both were shown, inferred

Data model (Postgres, not vector store):
- users (id, home_lat/lng, office_lat/lng, reliability_pref)
- trips (id, user_id, start_time, mode, origin_stop, dest_stop, predicted_arrival, actual_arrival, was_recommendation_followed)
- preferences (user_id, walking_tolerance_m, transfer_aversion_score, updated_at) — recomputed nightly from trips, not live

Why not vector memory / RAG: these attributes are structured and low-cardinality — a handful of numeric preferences per user, not unstructured documents to retrieve. RAG adds latency, cost, and a failure mode (retrieval returning the wrong "memory") for data that fits cleanly in five columns. Save the LLM for Phase 3, where its job is turning a decision into a sentence — not making the decision itself.

Architecture:
Android App -> FastAPI Backend -> PostgreSQL (trips, preferences) -> Nightly batch job: recompute preference scores from trip history

Exit criteria: the app can state, in plain data (not yet AI-phrased), "this user prefers reliability over speed, tolerates 0.3mi walks, prefers direct routes" — demonstrably derived from real usage, not defaults.

### Phase 3 — Four Named AI Features
Goal: Move from one generic "recommendation engine" to four distinct, purpose-built AI features that map onto the actual phases of a commuter's journey — each with its own trigger, its own job, and a shared brain underneath so they can never contradict each other.

The four features:

**Behavior AI** (foundation — not user-facing)
Learns from real usage rather than asking the user to configure anything. Three distinct signals, captured passively from existing app activity (viewing arrivals, favoriting, trip-logging — no new explicit action required):
- Feed accuracy: predicted vs. actual arrival time, per route/station/time-of-day — validates the *data source*.
- Route/direction choice: which direction or vehicle a user actually took, per station and time — validates *what to recommend this specific person*, not just "was the feed right."
- Personal timing buffer: how long before a train's predicted arrival this user actually starts moving.
Everything else in Phase 3 reads from this — it has to exist first, or Commute AI/Schedule AI/Chat AI's personalized half are just guesses with no data behind them.

**Commute AI** (routing decisions, in the moment)
Fires when the user opens a multi-option hub station (e.g. Journal Square) — a location-triggered, in-app event, not GPS. Infers the likely direction/destination from Behavior AI's history at that station and time, then recommends the fastest/most-reliable real option — "take bus 119 instead of your usual, it's 10 minutes faster today." Falls back to showing every direction unranked (never guesses) when there isn't enough history yet. This is the deterministic-scoring-engine-plus-narrow-LLM-phrasing pattern the original Phase 3 draft specified, generalized to be callable from more than one place (see the shared-brain note below) — a route's score is still predicted_arrival_time − (reliability_weight × recent_delay_variance), still explainable, still cheap to run per trigger. **Commute AI is the single, sole owner of "which route/mode is best right now" — no other feature re-implements this.**

**Schedule AI** (timing decisions, ahead of departure)
Fires on a schedule, ahead of the user's usual departure window (learned from Behavior AI's timing-buffer data, not a fixed clock time), and reacts to detected disruption on the user's known routine. Says things like "leave now," "leave 15 min later — usual bus is delayed," or "usual bus is cancelled, take X instead." **Schedule AI owns only the timing question — when to leave, how much buffer, whether a disruption is even worth interrupting the user about.** When a disruption forces a route substitution, Schedule AI delegates the routing choice to Commute AI's engine rather than re-implementing route-picking — this is what guarantees the two features can never recommend different things for the same disruption. Delivered as a push notification, since this is the one feature allowed to interrupt the user unprompted.

**Chat AI** (on-demand Q&A)
A conversational interface, user-initiated only (never proactive), split into two tiers:
- Stateless tier: answers questions using only live feed data ("what time's the next PATH train from Hoboken") — no dependency on Behavior AI, can ship independently and immediately.
- Personalized tier: answers questions that need history ("what do I usually take from here") by reading Behavior AI's data — gated on the same dependency as Commute AI, and **must give the same answer Commute AI would give if asked the same question in card form**, since both read from the one shared brain.
Chat AI must refuse plainly (never guess) on anything with no real answer in the data — fares, real-time crowding, anything outside the NYC-metro scope.

The shared brain: Commute AI, Schedule AI (when it needs a substitution), and Chat AI's personalized tier all call into one function — "given known alternatives, which is best right now, and why" — rather than each independently implementing scoring. This is a structural guarantee of consistency, not a convention to remember: it is architecturally impossible for two of these features to disagree about which route is best, because there is only one place that decision is made. Each caller differs only in *when* it calls (scheduled check / hub arrival / chat question) and *how* it phrases the answer (push / card / conversational reply) — never in the underlying ranking logic.

Trust-preserving design choices (carried forward from the original Phase 3 draft, and now shared across all four features rather than one):
- Always show the underlying numbers, not just the recommendation — Commute AI's card lists every real alternative it compared against, not just the winner.
- Track was_recommendation_followed and actual_arrival (feeds Behavior AI's feed-accuracy signal) so the app can honestly report its own accuracy over time.
- Confidence framing in language calibrated to the engine's actual confidence score, never overstated.
- The LLM's job stays narrow everywhere it appears: turn a decision a deterministic engine already made into a sentence. It is never asked to invent a number, a reason not reflected in the given data, or make the routing/timing decision itself.

Build order (dependency-driven): Behavior AI first (everything reads from it) → Chat AI's stateless tier in parallel (zero dependency, ships immediately) → Schedule AI (needs Behavior AI's timing-buffer data; mostly extends the notification job that already exists) → Commute AI (needs Behavior AI's direction-choice data specifically) → Chat AI's personalized tier (same dependency as Commute AI, lands alongside it).

Exit criteria: all four features are live and demonstrably reading from the same underlying scoring function — verified by confirming Commute AI and Chat AI's personalized tier give the same answer to the same routing question, and that a Schedule AI substitution never contradicts what Commute AI would have recommended at that moment. Recommendation accuracy (predicted vs. actual arrival) tracked and visible, per the original exit criterion.

## 7. Longer-Term Expansion (Phase 4+, architecture-only for now)
Because preferences, decision engine, and delivery layer are mode-agnostic, adding a new mode (driving, bike share, flights) is "add a data source + a scoring dimension," not a rebuild. Worth one paragraph in the pitch deck, not more — over-promising the "operating system for how humans move through cities" framing before Phase 1 ships risks reading as scope-inflation.

## 8. Key Risks
1. PATH data reliability — mitigated with graceful degradation, not solved
2. NJ Transit API approval lead time — apply immediately, treat as a Phase 1 blocker to sequence around
3. Cold start — Phase 3 recommendations are only as good as Phase 2's data; needs ~2 weeks of a user's own trip history before recommendations should be trusted
4. Wrong-recommendation cost is high — a bad output here has a real consequence (missed train), which is why the decision engine is deterministic and the LLM's scope is deliberately narrow

## 9. Tech Stack
- Mobile: Flutter
- Backend: FastAPI + PostgreSQL
- AI: Gemini/OpenAI API for phrasing only, low temperature, structured input
- Maps: MapLibre + OSM
- Data: GTFS-RT per agency, isolated per-feed error handling
- Addition: nightly batch job for preference recomputation, not live inference — keeps AI cost near-zero and the "learning" transparent and debuggable
